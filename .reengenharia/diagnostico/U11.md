# U11 — Diagnóstico por lentes: o harness de agentes

Base: `.reengenharia/unidades/U11-harness.md`, recorte `medida/U11.txt` (commit `08dc125`), roteiro `00-roteiro.md`. Tudo abaixo foi conferido no código por leitura; onde rodei algo foi só `node` importando funções exportadas de `revisoes.ts` (sem escrita, sem suíte). Marcas: [código] [medida] [doc] [hipótese].

## 1. Resumo

O harness tem uma parte forte e uma parte frouxa. A forte: o hook de commit e o portão (`revisoes.ts`, `mutacoes.ts`) são código tipado, com mais teste (3.211 linhas) que implementação (3.101), e a esteira falha fechada quando o GitHub some (`esteira.ts:175-181`). A frouxa: (a) o texto de instrução é grande demais e se contradiz (74 KB de base fixa, três contradições com a D79); (b) o contrato entre texto e hook é rótulo em markdown lido por regex, sem teste que olhe os templates, e quando o rótulo some o hook **afrouxa em silêncio**; (c) o hook só enxerga `git commit` escrito de um jeito, e uma falha dele na carga (não na lógica) deixa tudo passar. Complexidade, cobertura e clones da medição estão limpos (0 avisos; 3 clones, 1 real de 30 linhas entre `tools/vitrine` e `e2e/__fixtures__`). Quase tudo é Etapa 9; o que é seguro e o que é perigoso está na seção 7.

## 2. Achados (por impacto)

### U11-2 Falha do hook na carga é aberta: o commit e o push de branch protegida passam
- Lente: 5.4 resiliência
- Evidência: [código] `hook-revisoes.ts:22-36` só captura erro de `portao()`; `import` quebrado de `revisoes.ts`/`mutacoes.ts`, `node` sem type-stripping, ou arquivo ilegível derrubam o processo antes do `try`, sem `permissionDecision: deny`. `settings.json:24-34` não tem `timeout` nem `|| exit 2`. [hipótese] o Claude Code trata só `exit 2` como bloqueio e qualquer outro código como erro não bloqueante; confirma-se rodando uma sessão com um `import` quebrado numa cópia.
- Impacto: alto — o time roda de noite com `--dangerously-skip-permissions` (`seguir/SKILL.md:83-85`), e o hook é o único freio; um erro de sintaxe numa edição da Etapa 9 liberaria tudo sem aviso (RISCOS M5 pelo lado contrário do que está escrito: o risco não é só barrar, é soltar).
- Proposta: no `settings.json`, `node … portao || exit 2` (com a mensagem no stderr) e `timeout` explícito; um comando de "auto-teste" (`node tools/processo/hook-revisoes.ts --auto-teste`) que o `contexto-inicial.sh` roda no `SessionStart` e imprime se a carga falhou. **Fail closed** na carga.
- Custo: P
- Risco de mexer: alto — um `exit 2` errado bloqueia todo Bash de todo agente, e o agente ainda consegue consertar por `Edit`; teste a fazer: simular crash em worktree de teste. Hoje protege só `revisoes.test.ts`, que não cobre o ponto de entrada.
- Trava: teste que executa `hook-revisoes.ts` como processo com stdin fixo e confere a saída e o código de saída, inclusive com módulo ausente.
- Onda: 6 harness/docs
- Decisão do Joaquim: não

### U11-3 O hook só enxerga `git commit` e `git push` escritos em forma canônica
- Lente: 5.2 contratos | 5.4
- Evidência: [código] executei `ehCommit`/`destinoProtegidoDoPush` (exportadas): `git commit` e `git -c … commit` casam; `/usr/bin/git commit`, `command git commit`, `env X=1 git commit`, `sh -c 'git commit …'`, `bash ./c.sh` **não** casam; `git push origin develop` é barrado, `/usr/bin/git push origin develop` e `sh -c 'git push origin main'` não. `git cherry-pick`, `rebase` e `merge` criam commit sem passar (o merge de `linhas.ts:399-425` é intencional). O regex é `(?:^|[;&|(\n])\s*ATRIBUICOES git … commit` (`revisoes.ts:996, 1105`).
- Impacto: médio — o agente não é adversário, mas Sonnet à noite escreve `bash -c "cd x && git commit …"` sem pensar; um código sem revisor entra na branch e só a esteira vê.
- Proposta: normalizar o comando antes de casar (tirar `command`, `env`, caminho absoluto do git, desembrulhar `sh|bash -c '…'` recursivamente) e negar o comando que contém `git commit|push` dentro de script que o hook não consegue ler (`bash arquivo`) com a mesma mensagem de `antesDoCommit`. Alternativa mais robusta, para a Etapa 6.3: **Git hook nativo** `pre-commit` + `pre-push` (vale para qualquer forma de chamar o git, e não depende de parsear shell), com o PreToolUse só como mensagem melhor. Recomendo o git hook como camada de baixo.
- Custo: M
- Risco de mexer: alto — falso positivo trava o time; protege `revisoes.test.ts` (1.450 linhas, casos de `antesDoCommit`, `pastaDoCommit`, `pushDoTime`).
- Trava: casos de teste novos para cada forma acima (tabela de comandos × esperado).
- Onda: 6 harness/docs
- Decisão do Joaquim: NOVA: o git hook nativo entra como segunda camada da trava do commit? (muda onde a D23/D53 é aplicada e instala hook por checkout/andar)
